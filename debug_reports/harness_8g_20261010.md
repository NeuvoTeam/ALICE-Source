## B14 — the drawer still closes on selection

| Step | Observation |
| --- | --- |
| load at a 500x900 viewport (layout width 980px, i.e. below the 64rem/1024px `lg` boundary) | `button[aria-label="Open navigation"]` present; `isMobile` branch rendering |
| click the trigger | `[role="dialog"]` count 1, `data-state="open"`, the sidebar `<aside>` inside it |
| `window.__nav.setState({ selectedClientId: "client-2", selectedCaseId: "case-2", selectedSessionId: "sess-2" })` | `[role="dialog"]` count **0**; the drawer node is gone from `document.body` |

The selection write is the same store write the real navigation performs:
`components/sidebar/SessionNode.tsx:112` calls the store's `selectSession(caseId, session.id)` and
`app/dashboard/page.tsx:43` calls its `selectClient(...)`, which are exactly the two fields the old
effect (`[selectedClientId, selectedSessionId]`) reacted to. Screenshot: the shell after the close.

## B9 — History tab: spinner, failure banner, and no sticky banner

On the History tab, with the fetch stub switched per step (`window.__calls` counted the requests):

| Step | Spinner | "Failed to load sessions" | Row rendered | fetches |
| --- | --- | --- | --- | --- |
| refetch in flight (stub: 900 ms delay) | **1** | no | no | 2 |
| that refetch settled | 0 | no | **yes** | 2 |
| failing refetch (stub: HTTP 500, non-JSON body) | 0 | **yes** | yes (previous rows kept) | 3 |
| healthy refetch, in flight | 0 | **no** (cleared as soon as the key changed) | yes | 4 |
| that refetch settled | 0 | no | yes | 4 |

This is the behaviour the register's row B9 got wrong: `isLoading` starts `false` and `setError(null)`
was the only thing that ever cleared a previous failure, so neither pre-set was a bail-out. The
derived `requestKey`/`loadedKey` pair reproduces the old rendered states — including the spinner
during a refetch — while the banner is now keyed to the request that failed, which is why it cannot
stick after a failure that is never retried.
